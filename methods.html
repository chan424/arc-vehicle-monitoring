Count Methods

Methods

What this page is

The counter draws a line on a video and adds one vehicle each time a tracked box crosses it. Everything below is taken from this repository’s code and weight files, or from the papers and releases those files point at. Where a number was published by someone else, the sentence says so. This site has not measured its own accuracy on a labelled video, so it does not report one.

Where the work runs

The page is static. A Web Worker (worker.js) loads ONNX Runtime Web 1.22.0 (ort/ort.js, MIT Licence, Copyright Microsoft Corporation) and the chosen weights. The runtime binary is the concatenation of ort/runtime.part0.wasm and ort/runtime.part1.wasm, 21,872,216 bytes, passed in as ort.env.wasm.wasmBinary. The worker sets numThreads = 1 and proxy = false. One thread does not need cross-origin isolation, so GitHub Pages does not have to send COOP or COEP headers, and the .wasm response type is not used as a module thread. If the browser has WebGPU, the worker tries it, then compares the first real frame with a WASM session. A relative difference above 0.02, or a GPU failure, drops back to WASM.

Weights are stored as base64 inside JavaScript files so each piece stays under GitHub’s file-size limit. The worker reads the text, base64-decodes it, and checks the byte count. The video frames never leave the browser. An optional Google Apps Script address in config.js receives the signed-in operator and the count summary, not the video. If that address is empty, the page runs in preview mode and logs nothing.

An HLS link loads hls.js 1.5.17 from jsDelivr, and only then. That library is published under Apache-2.0. The typeface is Overpass, served by Google Fonts under the SIL Open Font Licence, with system fonts as the fallback. Neither is required for a count.

Bundled detectors

The Detector menu has three bundled files and a slot for your own ONNX file. The default is the Indian-traffic file.

Indian traffic — Ultralytics YOLO11s

Five files, uvh26_s.part0.js through uvh26_s.part4.js, decode to a 37,948,643-byte ONNX model. SHA-256 of those bytes is 56cfc7577c0def987ad14052220ad3f9695d9e939ca9d935a9b9be489d8cc143. The ONNX metadata stored in the file says:

  • Description: Ultralytics YOLO11s model trained on /home/vkovvali/dileepank/datasets/hackathon_blurred_1st_week/data.yaml
  • Author string: Ultralytics. Date: 2026-11-12T16:12:15.511265+05:30. Ultralytics version: 8.4.211.
  • Licence string in the file: AGPL-3.0 License (https://ultralytics.com/license)
  • Input size recorded in the file: [640, 640]. Export options include opset: 17, simplify: true, nms: false, end2end: false. The graph producer is PyTorch 2.15.0.
  • Class names, in order: Hatchback, Sedan, SUV, MUV, Bus, Truck, Three-wheeler, Two-wheeler, LCV, Mini-bus, tempo-traveller, bicycle, Van, Others.

That name list matches uvh_classes.txt published by AIM at the Indian Institute of Science with the UVH-26 models (Hatchback through Others, with tempo-traveller and bicycle in lower case). The training path contains hackathon_blurred_1st_week and a home directory vkovvali. Vijay Kovvali is an author of the UVH-26 technical report, which describes the Week 1 release of anonymised Bengaluru Safe City frames. Those two facts are consistent. This repository does not contain a checksum against the published UVH-26-MV-YOLOv11-S.pt file on Hugging Face, and that release is a PyTorch checkpoint rather than this ONNX file. The accuracy table further down is the paper’s table for their published YOLO11-S. It is not a measurement of this file.

The report is Sharma, Mhatre, Gawali, Bokkasam, Kishore, Pattanaik, Rambha, Pinjari, Kovvali, Chakraborty, Rathore, Krishnapuram and Simmhan, “The Urban Vision Hackathon Dataset and Models: Towards Image Annotations and Accurate Vision Models for Indian Traffic”, arXiv:2511.02563, November 2025. From that report, the dataset is 26,646 frames at 1080p, sampled from about 2,800 Bengaluru Safe City cameras over four weeks, annotated by 565 students, with about 1.8 million boxes. Consensus labels were made with majority voting (UVH-26-MV) and with STAPLE (UVH-26-ST). The public models described in the report were fine-tuned on the anonymised UVH-26-MV split. The dataset is released under CC BY 4.0. The report says the YOLO-family weights follow the AGPL-3.0 terms of the Ultralytics code they were fine-tuned from, while DAMO-YOLO and RT-DETRv2 weights in that release follow Apache-2.0. This site bundles only the YOLO11s ONNX file, not the dataset images and not the other five architectures.

The file declares AGPL-3.0, and Ultralytics distributes YOLO11 under AGPL-3.0. Serving those weights from a public site can count as network use of an AGPL program. This sentence records the licence string. It is not legal advice.

The repository is Apache-2.0. The ONNX headers name PyTorch 1.7 as the producer and do not store a class list. The page assumes the 80 COCO categories in the standard index order, and it keeps only bicycle (1), car (2), motorcycle (3), bus (5) and truck (7). Every other index, including person, is discarded. Ge, Liu, Wang, Li and Sun, “YOLOX: Exceeding YOLO Series in 2021”, arXiv:2107.08430. COCO is Lin and others, “Microsoft COCO: Common Objects in Context”, ECCV 2014. Megvii’s README for that release line reports COCO val box mAP at IoU 0.50:0.95 of 40.5 for YOLOX-S at 640, and 32.8 for YOLOX-Tiny at 416. Those numbers are Megvii’s COCO scores for the model variants. This site did not repeat the COCO evaluation, and a COCO score is not an accuracy for Indian CCTV.

On the General detectors only, a colour rule can relabel a car, bus or truck box as an auto-rickshaw. The box aspect ratio (height / width) must sit between 0.6 and 1.9, and at least 9 percent of a 20×20 colour sample must fall in an amber-to-yellow range (not dark, not grey, red at least 0.85× green, green at least 0.6× red, blue under 0.7× green). The rule is a heuristic in this page. It is not part of YOLOX, and it is off for the Indian-traffic model, which already has a three-wheeler class.

Your own ONNX file

A local .onnx file is read in the browser and is not uploaded. If the tail of the file contains an Ultralytics names dictionary such as {0: 'Hatchback', …}, those names are filled in. Otherwise you type them, in model order. Names are mapped with the same rules as the bundled Indian model. A file whose name contains “yolox” is decoded as YOLOX; anything else is decoded as an Ultralytics export (RGB, 0–1, letterbox centred on grey 114). Input sizes offered are 416, 512, 640, 800, 960 and 1280.

From a frame to a count

The default reads 12 frames per second of video time (the menu also offers 8 and 15). Recorded video is played only fast enough to keep the detector busy, between 1× and 4×. Live video and screen capture are sampled in real time whenever the detector is free. Hiding the tab pauses a recording, because browsers stop video in background tabs. A live source cannot be paused that way: seconds spent hidden are reported as missed, and the vehicles that passed then are not counted.

  1. Letterbox. The frame is scaled to fit the model square. Empty pixels are grey 114. YOLOX is pinned to the top left. The Ultralytics file is centred. YOLOX is fed as BGR in 0–255. The Ultralytics file is fed as RGB in 0–1. That split is in worker.js.
  2. Decode. YOLOX uses the anchor-free grid at strides 8, 16 and 32: centre is (offset + grid) × stride, size is exp(wh) × stride, and the score is objectness times the best class probability. The Ultralytics file has no NMS in the graph. Its output is read as [1, 4 + classes, N] or the transpose, and the score is the best class probability. Boxes under 4 pixels on a side are dropped. The decoder keeps anything at or above 0.12. That floor is fixed in the page; it is not the menu.
  3. NMS. Same-class boxes overlap-suppress at IoU 0.45. Different-class boxes suppress only above IoU 0.6, so a car and a truck on the same van do not both survive, while a rider beside a car still can. A box covering more than 20 percent of the frame, with score under 0.75, is dropped when it swallows a smaller box.
  4. Track. Boxes at or above the menu confidence (default 0.40) are matched first, by greedy overlap with a short constant-velocity prediction. A young track may also match by distance if the boxes are a similar size. Scores between 0.12 and the menu value are used only to extend a track that has already been seen twice. The class is a score-weighted vote, so a later, clearer view can change the label until you edit it by hand.
  5. Cross. The line has two sides. A track counts when its centre changes side, the crossing point lies on the segment (with a 3 percent slack), the track has been seen at least 3 times, it has moved at least half of its smaller side since it was born, and it is at least 0.4 of that smaller side past the line. Direction A is the positive side of the line as drawn; B is the other way. The arrow labels on the picture show which is which.
  6. One vehicle, one count. A track that dies and reappears on the line within about 2.5 seconds, close to an existing count in the same direction, is attached to that count instead of adding another. Two overlapping boxes that cross together (cab and body, rider and load) also share one count when the overlap is high, or when they voted for the same class and one box sits inside the other.

The flow rate is round(count / analysed seconds × 3600), and it stays blank until at least five seconds have been analysed. The chart picks a bin from 5 seconds up to 60 minutes so that a run has at most 36 bars. The share of each class is that class divided by the vehicles that have not been removed.

Exports

CSV and JSON contain the same count: a header, the class table, the time bins, the detector sub-class totals, and one row per vehicle that has not been removed. JSON adds the class id, whether the source was live, and how many rows were removed. It does not embed the thumbnail pictures. Copy table puts the same CSV, with tabs, on the clipboard. Hand-added rows are marked, and so are rows whose class you changed.

Sign-in

When config.js has an endpoint, the page asks for a name, an email and a 10-digit Indian mobile number, then a 6-digit code from that email. The session token is kept in localStorage under arc.session. During a run the page posts a summary: run id, video file name, duration, detector name, totals by class, the two direction totals and names, the correction count, the flow, and a shortened user-agent. It does not post pixels. Clearing the endpoint switches the whole log off and removes the sign-in gate. That is the preview mode described on the count page.

Limits

  • This is not a certified traffic census. A queue at a stop line, a camera that moves, rain, night, and vehicles hiding each other will each move the count. The page asks you to check a few minutes by hand before using the total.
  • No accuracy figure on this page was measured by running these ONNX files on a labelled set. The UVH-26 numbers are the paper’s. The YOLOX numbers are Megvii’s COCO numbers.
  • There is no tractor class in either bundled head. Goods three-wheelers and passenger autos share one three-wheeler class on the Indian model, and one auto tile on the screen.
  • YOLOX was trained on COCO photographs, not on Indian CCTV. It has no auto-rickshaw, LCV, mini-bus or tempo-traveller class except for the yellow-colour rule.
  • The first load of the Indian model plus the runtime is on the order of 60 MB of weights and runtime (about 38 MB and 22 MB), decoded in the browser. Later visits reuse the browser cache when the host allows it. Without WebGPU the larger models are slow; the page says so after a few frames and points at YOLOX-Tiny.
  • A direct video link plays only if that host sends CORS headers the browser accepts. YouTube and other players are counted by capturing the tab, and only while this tab stays visible.
  • Browsers generally will not decode AVI or arbitrary CCTV files. The page asks for MP4 (H.264), MOV or WebM.

What is unknown here

  • Whether the YOLO11s ONNX is a conversion of the exact Hugging Face file UVH-26-MV-YOLOv11-S.pt. The class list and the training-path name line up with UVH-26 Week 1. A checksum against that checkpoint was not made, because the published file is PyTorch and this one is ONNX.
  • The train and validation loss, the epoch, and the image counts inside hackathon_blurred_1st_week/data.yaml. That file is not in the repository. Only the path string is.
  • How this counter’s totals compare with a manual count on any particular road. That depends on the camera and the video, and it has not been measured in this repository.
